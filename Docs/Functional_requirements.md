# 1. Introduction

## 1.1 Purpose

The purpose of this project is to build an AI-powered SEO Automation Platform capable of automatically applying SEO improvements to an existing website repository using structured SEO intelligence generated from an external n8n workflow.

The platform will analyze a repository, understand its framework and page structure, determine appropriate SEO improvements, generate new SEO landing pages, safely update metadata, maintain sitemap.xml and robots.txt, and commit validated changes to Git.

The platform must preserve the existing user experience by ensuring that no user-visible content is modified.

---

## 1.2 Background

Marketing teams already perform keyword research, competitor analysis, search intent analysis, and SEO scoring through an existing n8n workflow.

Currently, developers manually perform tasks such as:

- Updating metadata
- Creating SEO landing pages
- Updating sitemap.xml
- Maintaining robots.txt
- Ensuring framework compatibility
- Creating Git commits

These repetitive engineering tasks will now be automated by this platform.

The AI platform consumes the SEO intelligence generated by n8n and performs repository modifications automatically.

---

# 2. Project Objectives

The system shall:

- Integrate directly with an existing n8n workflow.
- Accept SEO payloads through a FastAPI endpoint.
- Detect the framework used by the repository.
- Analyze all pages within the repository.
- Select the most relevant keywords for each page.
- Update only invisible SEO metadata.
- Generate SEO landing pages.
- Update or create sitemap.xml.
- Update or create robots.txt.
- Validate all generated changes.
- Retry failed implementations automatically.
- Commit approved changes to Git.
- Trigger the configured CI/CD pipeline.

# 4. System Overview

The platform consists of three primary components.

1. FastAPI API
2. SEO Planning Agent (Orchestrator)
3. OpenCode Execution Agent

FastAPI acts as the public API consumed by n8n.

The SEO Planning Agent is responsible for planning, validation, and review.

The OpenCode Execution Agent is responsible only for repository modifications.

The Planning Agent is the only component allowed to approve repository changes.

- Creating SEO pages.

# 11. Functional Requirements

This section defines the functional capabilities of the SEO AI Agent Platform.

The system shall execute the following workflow for every incoming request from the n8n workflow.

1. Receive the SEO payload from n8n.
2. Validate the payload.
3. Analyze the repository.
4. Detect the framework.
5. Analyze every page.
6. Select appropriate keywords for each page.
7. Generate an execution plan.
8. Execute the plan using OpenCode.
9. Review the generated changes.
10. Retry failed implementations if required.
11. Commit approved changes.
12. Trigger the configured CI/CD pipeline.
13. Return a structured execution report.

---

# 12. Input Payload

The platform shall consume the complete payload generated by the n8n workflow.

The payload is considered the source of truth for SEO intelligence.

The AI platform must never regenerate keyword research if it already exists in the payload.

The payload may include, but is not limited to:

- Target URLs
- Page information
- Seed keywords
- Keyword clusters
- Search intent
- Competitor analysis
- Keyword difficulty
- Search volume
- Ranking opportunities
- Meta title suggestions
- Meta description suggestions
- Internal linking suggestions
- Structured data suggestions
- Content recommendations

The payload schema should remain flexible so future additions do not require API changes.

---

# 13. Repository Analysis

Before planning any SEO modifications, the system shall perform a complete repository analysis.

The repository analysis phase is responsible for understanding the existing project before any modifications are attempted.

Repository analysis includes:

- Repository structure
- Framework detection
- Routing mechanism
- Metadata implementation
- Existing SEO implementation
- Existing sitemap.xml
- Existing robots.txt
- Existing SEO pages
- Public assets
- Build configuration

The analysis phase must complete successfully before execution planning begins.

---

# 15. Page Discovery

The platform shall discover every page within the repository.

Each discovered page should include:

- Route
- Physical file path
- Page title
- Existing metadata
- Canonical URL
- Headings
- Structured data
- Existing keywords
- Page purpose

The Planning Agent should understand the purpose of each page before assigning SEO keywords.

---

# 16. Keyword Selection

The Planning Agent is responsible for selecting keywords for every page.

The n8n payload already contains keyword intelligence.

The Planning Agent shall determine:

- One Primary Keyword
- Two Secondary Keywords

for every existing page.

Keyword selection must consider:

- Page intent
- Existing content
- Search intent
- Competitor analysis
- Relevance
- Keyword difficulty
- Search volume

The Planning Agent must record the reasoning behind each keyword selection.

Example:

Primary Keyword

Applicant Tracking System

Reason

The page primarily explains ATS functionality.

Secondary Keywords

- Recruitment Software
- Hiring Platform

Keywords should never be assigned randomly.

---

# 17. Metadata Optimization

The platform shall optimize invisible SEO metadata for every applicable page.

Allowed metadata updates include:

- HTML title
- Meta description
- Meta keywords (if used)
- Canonical URL
- Robots meta tag
- Open Graph tags
- Twitter Card tags
- Structured data
- JSON-LD
- Alternate language tags

Metadata should naturally incorporate:

- Primary keyword
- Secondary keywords

Metadata must remain concise, unique, and SEO optimized.

---

# 18. Existing Page Constraints

Existing application pages must remain functionally identical.

The platform shall never modify:

- Business logic
- UI components
- Navigation
- Styling
- JavaScript functionality
- API integrations
- Forms
- Authentication
- Application routing (except for new SEO pages)

Only invisible SEO-related improvements are permitted.

# 19. Human Visibility Protection

One of the primary project requirements is preserving the existing user experience.

The platform shall never modify any content visible to end users.

Forbidden modifications include:

- Headings
- Paragraphs
- Hero sections
- Buttons
- Labels
- Navigation
- Menus
- Product descriptions
- Pricing
- Testimonials
- FAQs
- Images
- Icons
- Calls to Action
- Form labels
- Table content

The only exception is newly generated SEO landing pages under the `/seo` directory.

# 20. SEO Landing Page Generation

The platform shall generate dedicated SEO landing pages using the SEO intelligence contained within the n8n payload.

Every generated page shall include:

- Optimized Meta Title
- Optimized Meta Description
- Canonical URL
- H1 Heading
- H2 Sections
- H3 Sections
- Semantic HTML
- Internal Links
- FAQ Section
- Schema.org Structured Data
- Competitor Comparison Section
- Call-to-Action
- Optimized content using selected keywords

The generated pages should follow the framework conventions of the target repository.

---

# 21. Competitor Comparison

Each generated SEO landing page shall contain a dedicated competitor comparison section.

The comparison should:

- Remain factual
- Avoid misleading claims
- Use the selected keywords naturally
- Highlight product strengths
- Maintain professional language

The platform must not fabricate competitor information.

If insufficient information exists within the payload, the comparison section should be omitted instead of hallucinating content.

---

# 22. SEO Directory Isolation

All generated SEO pages must exist exclusively within the `/seo` directory.

Examples:

/seo/applicant-tracking-system

/seo/recruitment-software

/seo/interview-scheduling

The platform must never generate SEO pages outside the `/seo` directory.

The physical implementation should adapt automatically based on the detected framework.

Examples:

- React Routes
- Next.js App Router
- Angular Routes
- Static HTML Files

---

# 23. SEO Page Quota

The `/seo` directory shall never contain more than ten pages.

Before generating new pages, the platform shall inspect the existing `/seo` directory.

If generating additional pages would exceed the limit, the platform shall automatically prune pages.

Pruning priority:

1. Oldest generated page
2. Least recently modified page
3. Lowest priority page (if metadata available)

The pruning process shall only affect generated SEO pages.

No application pages outside `/seo` may be removed.

---

# 24. Sitemap Management

The platform shall manage sitemap.xml automatically.

If sitemap.xml exists:

- Parse the file
- Preserve existing URLs
- Add newly generated SEO pages
- Remove URLs belonging to deleted SEO pages
- Preserve formatting where possible

If sitemap.xml does not exist:

- Create a valid sitemap.xml

Each generated SEO page should be included with:

- URL
- Last modified timestamp
- Change frequency
- Priority

---

# 25. robots.txt Management

The platform shall automatically manage robots.txt.

If robots.txt exists:

- Preserve existing rules
- Add sitemap reference if missing
- Ensure generated SEO pages remain crawlable

If robots.txt does not exist:

- Create a valid robots.txt

The generated file should include:

- Sitemap location
- Appropriate crawl permissions
- Standard SEO directives

# 26. AI Agent Architecture

The platform shall use exactly two AI agents.

No additional planning or execution AI agents shall be introduced.

Any additional functionality must be implemented as reusable services, helper modules, validators, or utilities rather than separate AI agents.

The two AI agents are:

1. SEO Planning Agent (Orchestrator)
2. OpenCode Execution Agent

---

# 27. SEO Planning Agent (Orchestrator)

## Purpose

The SEO Planning Agent is the central intelligence of the platform.

It is responsible for understanding the repository, interpreting the SEO payload, planning repository modifications, validating generated code, and deciding whether repository changes should be accepted.

The Planning Agent is the only component authorized to approve repository modifications.

It never edits repository files directly.

---

## Responsibilities

The Planning Agent shall:

- Receive requests from the FastAPI API.
- Validate the incoming payload.
- Analyze the repository.
- Detect the project framework.
- Analyze every page.
- Select one primary keyword and two secondary keywords for each page.
- Determine which pages require metadata updates.
- Determine which SEO landing pages should be generated.
- Determine whether pages need to be pruned.
- Generate an execution plan.
- Send the execution plan to the OpenCode Execution Agent.
- Review all generated modifications.
- Generate corrective feedback if validation fails.
- Retry failed implementations.
- Approve successful implementations.
- Create Git commits.
- Trigger the configured CI/CD pipeline.
- Return the final execution report.

---

# 28. OpenCode Execution Agent

## Purpose

The OpenCode Execution Agent is responsible only for modifying the repository according to the execution plan received from the Planning Agent.

It performs no planning, reasoning, or approval.

It simply executes tasks.

---

## Responsibilities

The OpenCode Execution Agent shall:

- Update metadata.
- Create SEO landing pages.
- Update sitemap.xml.
- Update robots.txt.
- Create framework-specific routes.
- Generate framework-specific files.
- Delete pruned SEO pages.
- Return execution summaries.
- Return modified file lists.
- Return generated file lists.
- Return deleted file lists.
- Return execution errors if any.

---

# 29. Execution Workflow

The execution workflow shall follow the sequence below.

1. Receive HTTP request.
2. Validate payload.
3. Analyze repository.
4. Detect framework.
5. Analyze pages.
6. Select keywords.
7. Generate execution plan.
8. Execute modifications using OpenCode.
9. Review generated changes.
10. Approve or reject modifications.
11. Retry if necessary.
12. Commit approved changes.
13. Trigger pipeline.
14. Return execution report.

This sequence shall remain consistent for every execution.

---

# 30. Review Workflow

Every repository modification produced by the OpenCode Execution Agent must be reviewed before being accepted.

The Planning Agent is responsible for the review.

The review shall verify:

- Metadata correctness
- Framework compatibility
- Repository safety
- SEO quality
- Sitemap correctness
- robots.txt correctness
- Directory constraints
- Human visibility constraints
- Brand relevance

No repository modifications may be committed without successful review.

---

# 31. Retry Mechanism

If review fails, the Planning Agent shall generate corrective instructions.

These corrective instructions shall be sent back to the OpenCode Execution Agent.

The OpenCode Execution Agent shall regenerate the required modifications.

The review process shall repeat.

Maximum retry attempts:

3

If all three attempts fail:

- No Git commit shall occur.
- No pipeline shall execute.
- The API shall return a failed execution report.

---

# 32. Review Criteria

The Planning Agent shall reject repository modifications if any of the following conditions are detected.

## Metadata Issues

- Duplicate titles
- Duplicate descriptions
- Missing canonical URLs
- Invalid structured data
- Keyword stuffing
- Missing metadata

---

## Repository Safety Issues

- Modification outside approved directories
- Unexpected file deletion
- Unexpected routing changes
- Invalid file creation
- Invalid framework implementation

---

## SEO Issues

- Poor keyword placement
- Duplicate keywords
- Low-quality metadata
- Missing schema
- Invalid internal links

---

## Human Visibility Issues

- Visible headings modified
- Visible paragraphs modified
- Buttons modified
- Navigation modified
- Product content modified
- Pricing modified
- Hero section modified

---

## Brand Relevance Issues

- Content unrelated to company
- Hallucinated product features
- False competitor claims
- Invalid service descriptions

# 33. Guardrails

The platform shall enforce the following guardrails before approving repository modifications.

## Repository Guardrail

Only approved files may be modified.

Forbidden:

- Package changes
- Dependency changes
- Build configuration changes
- Application logic changes

---

## Human Visibility Guardrail

User-visible content must remain unchanged.

Forbidden modifications include:

- Headings
- Paragraphs
- Buttons
- Labels
- Navigation
- Menus
- Images
- Product descriptions
- Pricing
- Testimonials
- Forms
- Existing FAQs

Only invisible SEO metadata may be updated.

---

## SEO Quality Guardrail

The generated metadata must:

- Be unique
- Be concise
- Avoid keyword stuffing
- Follow search engine best practices
- Match page intent

---

## Framework Guardrail

All generated code must follow the conventions of the detected framework.

Examples include:

- React JSX
- Next.js App Router
- Angular Components
- Vue Single File Components
- Static HTML

Generic implementations are not permitted.

---

## Brand Relevance Guardrail

Generated content must:

- Match the company's domain.
- Match existing products.
- Match existing services.
- Use consistent terminology.
- Avoid fabricated claims.

---

## Directory Guardrail

Generated SEO pages must exist only within:

/seo

No generated pages may exist elsewhere.

---

## Page Limit Guardrail

The `/seo` directory shall never exceed ten pages.

If required, the oldest generated pages shall be removed automatically before creating new pages.
